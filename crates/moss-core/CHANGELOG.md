# Changelog

All notable changes to this crate are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **`sort::cmp_labels`** — the one comparator for ordering user-visible listing labels by title. Case is a tiebreak, not a primary key, so `mao` now sorts between `Kayla` and `Scarly` instead of after every capitalised name. All title-axis and dateless-tiebreak label sorts now route through it.

## [0.15.0] - 2026-09-06

### Fixed

- **A language-suffixed index is titled by its folder.** `heading::filename_text_with_root` applies the one home-file rule, so `essays/index.zh-hans.md` reads "essays" in `<title>` and chrome like its bare twin, instead of "index.zh hans".

### Changed

- **BREAKING:** **`terms::AUTHOR_NS` is `authors`** (was `author`), so generated author pages serve at `/authors/<slug>/` and `term_folder_key` yields `authors/<slug>`, matching `tags/`. The schema descriptions for `author` and `author_page` name the new path. A site that published the old URL gets no redirect: a generated page has no uid for the redirect machinery to key on.

## [0.14.0] - 2026-09-02

### Added

- **`terms` module — the single owner of term identity** for the new author/tag term pages. `term_fold` (trim + lowercase equality), `term_slug` (URL segment; dots become hyphens so the slug survives the render side's path slugger), `term_folder_key` (`author/<slug>` / `tags/<slug>`), and `TermClaim` (the resolved form of `author_page:`/`tag_page:` — `UseTitle` or an explicit `Name`). `merge_tag_lists` moved here from moss-build's markdown pipeline; same behavior (frontmatter first, inline tags appended case-insensitively, both-absent stays `None`).
- **`FrontMatter.author` is now `Option<Vec<String>>`** (was `Option<String>`), deserialized leniently: a single string stays one verbatim entry ("A and B" is not split), a YAML list gives one entry per item. A single entry serializes back to the plain-string form, so round-trips don't rewrite existing files.
- **`FrontMatter.author_page` / `FrontMatter.tag_page`** (`Option<TermClaim>`) with matching `BUILTIN_FIELDS` entries (OneOf boolean|string, like `children`), and `frontmatter_union::normalize_name_list` / `normalize_term_claim` as their shared editor/build normalizers.

## [0.13.1] - 2026-09-01

### Changed

- **`--moss-sidenote-reserve`'s contract description now matches what core does with it.** The property is the note gutter's width; core no longer pads `<body>` by the whole of it. It derives `--moss-sidenote-inset` — `clamp(0px, calc(2 * reserve + content-width - 100vw), reserve)` — and pads by that, so a page gives up only the width the window is short of fitting the gutter: nothing from about 1316px up, and every centred block moves half of whatever is given up. A theme overriding the reserve to widen or narrow the note column still works unchanged; the inset follows it. `--moss-sidenote-inset` is internal plumbing and deliberately carries no `CUSTOM_PROPS` row — it is read without a fallback, which is what keeps it out of the theme-hook catalogue.

## [0.13.0] - 2026-09-01

### Added

- **The reading scale — `--moss-read-title`, `--moss-read-h1`..`--moss-read-h6`, `--moss-read-caption`, and `--moss-reading-script-scale`.** Prose typography is now expressed as ratios of `--moss-reading-size` instead of as absolute sizes, so headings, body and captions move together when a reader uses the font-size control or when a Chinese page takes the +6% CJK size bump. Before this, three different bases were in play — absolute `rem` for headings, `--moss-reading-size-base` for `h4`, `--moss-reading-size × 1.06` for CJK body — and only one of them moved, which is why `h4` rendered below body text on every Chinese page and `###` shrank below body as soon as a reader enlarged the type. `--moss-reading-script-scale` is the per-script multiplier (1, and 1.06 under `html[lang^="zh"]`), folded into `--moss-reading-size` so everything built on that size inherits it. A theme retunes prose by overriding a ratio. `--moss-size-*` keeps its desktop values and stays chrome geometry, with one consequence worth naming: the mobile `:root` block no longer lowers `--moss-size-2xl` and `--moss-size-3xl`, because prose no longer reads them. `--moss-size-2xl` therefore resolves to 26px under 48rem where it previously resolved to 24px. Nothing in moss's own output consumes it at that width — every `<h1>` moss emits is claimed by a more specific rule — but a theme that reads `--moss-size-2xl` directly will see the change.

### Removed

- **BREAKING:** **`--moss-size-3xl`.** Declared, overridden once for mobile, and referenced by nothing. A theme reading it now gets the property's inherited or initial value rather than 32px; `--moss-size-2xl` (26px) is the largest remaining step of that scale, and prose titles use `--moss-read-title`.

## [0.12.0] - 2026-08-30

### Added

- **`asset_paths::VIDEO_LADDER` and friends — the video delivery ladder, alongside the image `LADDER`.** `VideoRung { width, height, fps, video_kbps, audio_kbps, audio_channels }`, the six-rung table, `video_ladder_rungs(source_width)` (truncated from the top only, by the same `take_while` shape the image ladder uses, and never to nothing), `video_top_rung`, `video_ladder_fingerprint` for cache keying, and `MIN_BITS_PER_PIXEL_PER_FRAME`. One table states the floor, the rungs and the ceiling together, so they cannot drift apart: the top rung *is* the delivery ceiling, and a test rejects any rung that falls under the floor. The bottom rung sits below Apple's published bottom and runs at 15 fps — an iPhone on a link delivering 118–232 kbps could not start Apple's leanest arm, and halving the frame rate is what buys enough bits per frame for 45 kbps at 320x180 to be a picture rather than a smear. Audio is a rung property rather than a separate setting, because pairing a lean rung with a 192 kbps track makes it unreachable however small the picture gets.

- **`asset_paths::video_ladder_rungs_by_count` and the HLS layout.** A ladder is one directory named after the video — `to_hls_dir`, `to_hls_master`, `HLS_MASTER_NAME`, `hls_members`, `hls_outputs` — and every file inside it has a constant name, so nothing the encoder writes mentions the video it came from. That is what lets a cached ladder be relinked under a renamed video: the playlists reference their siblings by name, and the names do not change. `hls_master_stem` is the inverse, recovering the source stem from a master URL so the registry can tell a ladder from any other playlist without guessing. `video_ladder_rungs_by_count` is the inverse of `video_ladder_rungs`: the ladder truncates from the top only, so a ladder's length names its rungs, and a cache holding one can identify it without re-reading the source it came from.

- **`attachment` — the `[editor].attachment_folder` path rules, moved here from moss's host.** Three functions over the one stored string that says where a page's images live: `attachment_dir_for_page(raw, page_rel)` (where an image dropped on that page should land), `is_attachment_dir(raw, dir)` (the inverse — is this directory storage rather than a section of the site?), and `validate_attachment_folder(raw)` (rejects absolute paths and `..`). Also `is_rooted(path)`, the platform-independent "would this escape the project root?" test the validator uses, exported because it is the one owner for every caller that asks. `""` means attachments sit beside the page, and then `is_attachment_dir` is false for everything.

- **`link_completions::asset_ref_relative` — the reference form for an asset, written from a given page.** The asset arm of `insert_for`, lifted out so a file *picker* can share it with the search dropdown. Same invariant: it emits the form whose first applicable resolver step reproduces the path exactly — source-relative when the asset lives in the page's own subtree, `/`-rooted otherwise. Unlike `insert_for` it never returns `None`: a typed query without a `/` implies no path, but a file the author pointed at directly always has an exact answer.

- **`frontmatter::frontmatter_span` — one answer to "where does this file's frontmatter end?", for both dialects.** Returns `FrontmatterSpan { kind, fields, body }` with byte offsets into the ORIGINAL string: no CRLF normalization, no BOM rewrite, so a caller can splice into the author's file without re-emitting it. moss had eleven independent splitters and nine of them saw only the `---`-delimited dialect, so a file written in the simplified dialect (a prefix of `key` / `key: value` lines closed by a standalone `---`) came back as "no frontmatter" and its field lines were handed downstream as body text. Every splitter in the crate and in moss now reads this one. `FrontmatterKind` says which dialect was found.

- **`frontmatter::frontmatter_map` — frontmatter as an untyped map, for either dialect.** `parse` answers the `---`-delimited dialect only, because its `ParsedDocument` also carries a byte-for-byte body and a delimiter range that only that shape has. A caller that just wants to read a field wants this instead. A bare flag is `true`; a simplified value is coerced only when YAML reads it as a scalar, so `date:` and `home:` mean the same thing in both dialects while `children: [[News]]` stays the string the author typed.

### Changed

- **`contract::custom_props` — `--moss-sidenote-reserve` no longer describes a gutter reserved on every page.** The margin-note gutter is now scoped out of a site's front page as well as full-width and sidebar pages, and `.moss-hero` reads the property to add the reserve back to its own width. A theme that set the property by hand is unaffected; a theme that assumed every page of a footnoted site carried the same right padding is not. The reserve buys consistency between pages a reader experiences as the same layout, and a front page — hero, card grids, no reading column — was paying a 140px shift and a 280px empty margin for a benefit it cannot collect.

- **`frontmatter::parse` no longer claims a document that merely opens with `---`.** The opening line must now be exactly `---` (leading BOM allowed, trailing whitespace allowed). Previously any first line *starting* with `---` opened a block, so a document beginning with the thematic break `----` was read as frontmatter, failed to deserialize as a mapping, and `render_body()` then dropped everything above the next `---`. An indented `   ---` — a legal CommonMark thematic break — is likewise no longer an opening delimiter. `frontmatter_asset_spans` picked up the same rule, and now covers the simplified dialect too.

- **`ast::footnotes` now emits `tabindex="-1"` on both the footnote marker (`<sup class="moss-footnote-ref">`) and the endnote item (`<li id="fn-N">`).** A `:target` fragment jump (forward to the note, backward to the marker) must move keyboard focus, not only scroll position — an unfocusable target leaves the reader's tab order stranded at whatever they clicked. Both elements were already valid fragment-navigation targets by id; this makes them programmatically focusable so the browser actually parks focus on arrival.

### Removed

- **`frontmatter_typed::simplified_frontmatter_delimiter`.** Its answer is `frontmatter_span(content)`, whose `fields.end` is the same offset and which also says which dialect it found. `is_simplified_frontmatter`, `simplified_frontmatter_keys` and `parse_simplified_frontmatter` are unchanged in signature and now read that one span.

## [0.11.0] - 2026-08-21

### Changed

- **`contract::COMPONENTS` now declares every class moss emits, not just the prefixed ones.** The table held 92 of the 189 classes moss ships. The scanner behind `components_sync_test` only inserted a class if it began with `moss-` (plus the callout and main-nav families), so the whole `comment-*` and `review-*` families, the lightbox and media-collection page, `link-preview*`, and the bare co-classes `active`, `title`, `empty`, `minimal`, `size-std` and `wikilink` could be renamed, mistyped or dropped with the suite still green. 44 new entries close that, each carrying its parent, an example and a description written from the emitting call site rather than from the name. Two classes are allowlisted instead — `d` and `f`, which belong to the standalone Jupyter iframe wrapper that moss generates whole with its own scoped inline styles, unreachable by any site stylesheet or theme. The bar for that list is deliberately high: a class in a page moss builds is contract, however short its name. Consumers reading the table see more entries; no emitted markup changed.

### Fixed

- **The sync test reads markup the way a browser does, so three real gaps became visible.** `components_sync_test` matched `class="..."` on a bare quote only, so it never saw markup emitted through an ordinary Rust string literal — where the attribute reads `class=\"...\"` — which is how twenty emitter files write it. It also read doc comments as if they were emitted markup, and scanned `site.css` and its `site/` partials while ignoring the three feature stylesheets shipped alongside them (`comments.css`, `review.css`, `email.css`). With the matching fixed: `moss-embed-pending` (the co-class on an embed still arriving from iCloud, emitted since the cloud gate landed) and `moss-subscribe-script` are now governed, and `.moss-subscribe-description` was deleted from `email.css` — the emitter stopped producing it when description moved out of the shortcode into prose, and the stylesheet had gone on shipping rules for markup that no longer existed.

## [0.10.0] - 2026-08-20

### Added

- **`html_entities::decode` — one decoder for text that arrives HTML-escaped.** Three callers in moss needed the same small thing and none of them is an HTML parser: the article scraper reads JSON-LD out of a `<script>` block, so titles arrive as `China&#8217;s`; the build's HTML post-pass has to decode an attribute value before it can split a URL on `?`/`#`, because a `#` inside `&#39;` is not a fragment; and the orphan sweep compares an author's media reference against filenames, where `&amp;` is not one. Deliberately not a full entity table — numeric references in both spellings (`&#8217;`, `&#x2019;`) plus the named entities an escaper emits (`&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;`, `&nbsp;`). Total by construction: an unknown token, a bare `&`, or an unterminated entity passes through byte-for-byte, so `Cats & dogs` comes back unchanged.
- **`moss-border-strong` design token.** The border for an element whose boundary *is* the control — the `.moss-input` underline — meeting the WCAG 1.4.11 non-text-contrast threshold of 3:1 against the page. `moss-border-light` and `moss-border-medium` stay decorative hairlines and stay exempt; reach for this one only when the user must see the boundary to operate the thing.
- **`moss-skip-link` component entry.** The first focusable element in `<body>`, ahead of the nav island and header: visually hidden at rest, visible on `:focus`, and jumping to `<main id="main-content">` (WCAG 2.4.1). A theme may restyle it, but should keep it off-screen until focused.

### Changed

- **BREAKING (emitted CSS): `moss-color-accent-quiet` is now a `{light, dark}` pair rather than a single value.** It was one of only two colour tokens still carrying a single value for both themes, which meant a dark page composited a light-tuned hairline. Anything reading `tokens.json` and assuming `$value` is a string for this token must handle the object form — every other token already used it. Its contract also now states the limit that was previously only folklore: it is ambient only and is **never** a focus indicator, because it composites too close to the page to satisfy 1.4.11. Use `moss-color-ui-accent` for focus.
- **Six token values darkened to meet WCAG contrast** — `moss-color-muted`, `moss-code-accent-tertiary`, `moss-code-accent-quaternary`, `moss-hl-comment`, and `moss-hl-meta`. These are not decoration: `moss-color-muted` is body text at 14px in roughly thirty places, and a code comment is text a reader is expected to read, so neither is exempt from 1.4.3. All now meet 4.5:1 against the backgrounds they actually appear on. Sites and themes inherit the new values automatically; a theme that hard-codes the old hexes keeps its old contrast.
- **`synthesize_image_html` now honors `extra_attrs` for `ImageContext::SiteLogo`.** The site-logo branch built its tag by hand and silently dropped the caller's extra attributes, so the editor preview's `data-source-fm="logo"` annotation never reached the logo — on the homepage that declares `logo:`, it was the one image with no way back to the frontmatter field behind it. The attribute rides directly after `class`, and `None` reproduces the previous byte shape exactly, so existing snapshots are unaffected.

## [0.9.0] - 2026-08-13

### Added
- **`contract::shortcodes` — the authoring catalog: what shortcodes exist, what attributes each takes, and which of those attributes name an asset file.** A `COMPONENTS`-style table, in the same spirit and for the same reason: the editor's slash menu and fence autocomplete used to hand-copy this knowledge into TypeScript, and the copies drifted (`apply` was missing from one of them). The table is emitted to `frontend/app/editor/shortcodes.generated.ts` and diff-gated in CI, so a Rust-side shortcode change cannot land without the generated copy following. Public items: `ShortcodeCatalogEntry`, `ShortcodeAttrSpec`, and `entry()`, whose match is total over `ShortcodeKind` — adding a variant fails compilation here until the catalog describes it. Presentation is deliberately absent: labels, hints and translations stay with the host, which overlays its own i18n on the structural catalog.
- **`ShortcodeKind::name()`, `ShortcodeKind::authorable()` and `ShortcodeKind::all()`.** `name()` is the fence name authors write after `:::`, pinned by a unit test to the serde `snake_case` form. `authorable()` is whether editors should offer the shortcode at all — `apply` parses and renders but is never suggested, because it is the membership application form and is meaningful only on sites configured for it. That decision now lives in Rust once, rather than in each editor surface that has to respect it.

## [0.8.0] - 2026-08-10

### Added
- **`GridCellParts::cover_color`, so a hand-built grid cell can wear the same colour band a collection card gets.** A `:::grid` cell that opens with an image now publishes that image's dominant colour as `--moss-cover-color` in the card wrapper's `style`, alongside a `data-cover-color` presence flag — the same custom property, on the same class, that a collection card already carries. moss-core paints nothing with it and never computes it: reading pixels is I/O, so the host fills the field in and this crate only decides where the bytes land. Absent for a cell with no leading image, and for one whose file moss could not read. **BREAKING** for anything constructing `GridCellParts` with a struct literal — add `cover_color: None`, or go through `GridCellParts::from_html`, which is unchanged.
- **`DefaultHooks::grid_cells`**, the hook set for rendering the blocks of a `:::grid` cell. Same reasoning as `hero_overlay`: a heading in a cell is that card's title, not a section of the page, so it gets no permalink anchor. It also closes a hole — grid cells render through `DefaultHooks`, whose trait defaults said anchors-on and English-label, so a cell heading carried a `#` even on a site with `heading_anchors = false`, and an English `aria-label` on a non-English site. Neither was visible from the host side, which reads its own hook overrides and never sees the ones a delegated render uses.
- Eleven `COMPONENTS` entries for attributes the site JavaScript reads (`data-cover-color`, `data-share-cover`, `data-type`, `data-src`, `data-title`, `data-article`, and the four comment-identity attributes), plus entries for `container`, `nav-content`, `font-anchor`, `font-trigger`, `cover-thumb`, `media-item`, `lightbox-content` and `lightbox-image`. These classes were already emitted and already read by shipped JS; they simply were not in the table, so `moss describe --json` and `contract.md` under-reported the contract.

### Changed
- **BREAKING (emitted HTML): the heading permalink anchor is now empty.** `render_heading` emits `<a class="moss-heading-anchor" href="#id" aria-label="…"></a>` — the `#` a reader sees is drawn by `site.css` as `::after` content. A real text node is excluded from the clipboard by Blink but **not** by WebKit, so on Safari, and in moss's own WebKit preview, selecting a heading copied "Introduction#". Generated content is the only form of the glyph no engine will copy. Measured in both engines 2026-08-09. Anything asserting on the anchor's inner `<span aria-hidden="true">#</span>` must drop it; the element, its class, its `href` and its `aria-label` are unchanged.
- `--moss-cover-color`'s contract description now also covers the grid-card case above. Description text only.

## [0.7.0] - 2026-08-09

### Added
- **`ResolvedSort::presentation_axis()` — the axis a listing's cards present with, as opposed to the axis they order by.** A folder with an explicit `sort: [list]` is a hand-ordered sequence — an award's parts, a series — not a chronological feed, so its cards should not carry the per-card date that a Date-axis listing shows. The ordering machinery already treats an explicit list as curated (`series_default`, no date re-sort); this method gives renderers the same answer for presentation: Weight when `explicit_order` is set, otherwise the resolved axis. `ResolvedSort`'s fields are unchanged.

### Changed
- **The editor scan now says WHICH grid divider used the old `---` spelling, not just that one exists somewhere.** `EditorShortcodeBlock::dividers` changed type from `Vec<EditorRange>` to `Vec<EditorDivider>`, a new public struct pairing the same range with a `legacy: bool`. A document-wide flag cannot tell an editor where to put a hint, and a hint that cannot point at the line it is about sends the author hunting. `EditorScanResult::legacy_dash` is unchanged and still answers the cheap document-level question. **BREAKING** for anything that read `block.dividers[i]` as a range: read `block.dividers[i].range`. Nothing about what moss accepts changes — `---` still builds, and the build's deprecation warning is untouched.
- **One rule for what frontmatter reaches the page: a field that exists only to be displayed is displayed, on every page kind. Everything else is metadata, and the body is the author's.** Two exceptions are gone. `moss-collection-description` is removed from `COMPONENTS`: `description:` no longer renders as a visible standfirst under a folder title and is metadata again everywhere — `<meta>`, `og:`, `twitter:`, JSON-LD. It had no stable provenance (sometimes authored, sometimes derived from the body by moss's own fallback chain), so a reader could not tell whose sentence it was and an author could be shown words they never wrote. Going the other way, `byline:` and `colophon:` now describe themselves — in `schema_fields.rs` and in `COMPONENTS` — as page-level rather than article-level: they render on folder-index pages too, with the same placement and the same classes. Removing a `COMPONENTS` entry changes `moss describe --json` and `contract.md`; nothing else in the crate's API moves. Note the standfirst existed for exactly one version — it was added in 0.6.0, above, and is removed here. The rule now holds with no page kind left out: the `moss-byline` and `moss-article-colophon` entries describe credits as rendering on the homepage and on plain pages too, and say where the byline lands on a page moss gives no title of its own (under the author's own opening heading, or at the top of the page). Description text only — no class, structure or API changes.

### Fixed
- **A grid with column proportions now collapses on a phone like any other grid.** `:::grid 2 1:2` emitted `style="grid-template-columns:1fr 2fr"` on the container. An inline declaration outranks every rule in every stylesheet, so the responsive rule that folds a grid to one column below 768px could never reach a ratio grid — it stayed two columns at every width, down to a 320px screen. The proportions now ride as the custom property `--moss-grid-ratio` (`minmax(0, 1fr) minmax(0, 2fr)`), which the stylesheet reads through `grid-template-columns: var(--moss-grid-ratio, …)`, putting the value back under the cascade where a media query — or a theme — can override it. `minmax(0, …)` rather than a bare `fr` for the same reason the fixed-count grids use it: a bare `fr` track floors at its content's intrinsic width, so one wide image used to push the page sideways. Affects the `Shortcode::Grid` opening tag only.
- **A grid inside a grid now keeps its own cells.** Writing `::::grid` around a `:::grid` is the nesting the grammar tells authors to use, and the fences did nest correctly — but the cell splitter did not care whose fence it was inside. It split the outer grid's body on *any* `+++` it found, so the inner grid's dividers cut up the outer grid instead: a one-column outer grid came back with two cells, each holding half of the inner block's source. Nothing warned, and the page built and looked plausible, which is why it survived. `split_grid_cells` now tracks nesting the way `editor_scan` already did — an opener pushes its arity, a matching closer pops it — and only honours a divider at the grid's own depth. Same treatment for a `+++` inside a code fence or an HTML comment: those lines are inert everywhere else in the extractor, and now here too, so a grid cell that *documents* the `+++` syntax stops tearing itself in half. Unlike the same-arity case below there is no ambiguity about what the author meant, so this parses rather than warns; correctly-nested arities stay silent. A `---` belonging to a nested block no longer raises the outer grid's deprecation warning either — it is reported when that block is parsed. No API changes.
- **Nesting a `:::` block inside another `:::` block now says so instead of quietly wrecking the page.** The inner block's closing fence was being taken as the outer block's, so the outer ended early and everything after it — `+++` dividers included — spilled into the prose as literal text. The page built, exit code 0, no warning; the only clue was a stray `+++` in the output (#1014). `ExtractionResult::warnings` now carries a line naming the block that ended early, the nested opener that took its fence, and the fix to type: one more colon on the outer fence (`::::grid` … `::::`), nested fences left alone. Keyed strictly on a nested opener with the **same** colon count as the block it sits in, seen before that block's closer — the one arrangement in which first-closer-wins misattributes a fence. A higher-arity inner (`:::grid` around `::::buttons`) and a higher-arity outer (`::::grid` around `:::`) are both supported nesting and stay silent, as does every document with no nesting at all. **What parses is unchanged**: same AST, same HTML, same `---`/`+++` handling. This is a diagnostic only.
- **A captioned image is no longer described twice to a screen reader.** `![[cover.jpg|Photo: the memorial wall]]` and `![Photo: the memorial wall](cover.jpg)` put the same sentence in the `<img alt=>` and in the `<figcaption>`, so assistive tech announced it once as the image's accessible name and again as the caption. There is only one authored string, and when it is visible as a caption the caption owns it: the `Block::Figure` renderer now emits `alt=""` on an image whose figure actually carries a `<figcaption>` (the standard pattern for an image described by adjacent text). Keyed on the emitted caption, not on the node, so an image with **no** caption is untouched and keeps the alias as its only accessible name — an inline embed inside prose, and every image on a site with `implicit_figure = false`. The `Inline::Image.alt` string itself is unchanged; only the emitted attribute differs.

## [0.6.0] - 2026-08-08

### Added
- **Two frontmatter fields, `byline` and `colophon`.** Both are credit rows an author writes — one per line of a block scalar, or one per list entry — rendered as inline markdown so a row may carry links. `byline` lands under the article title, `colophon` at the foot. They are display strings, not structured data: moss makes no machine claim about who did what, and neither field is connected to `author`. Adds `FrontMatter::byline` and `FrontMatter::colophon` (both `Option<Vec<String>>`), the public helpers `frontmatter_union::normalize_credit_rows` and `deserialize_credit_rows`, and two `BUILTIN_FIELDS` entries — so `builtin_schema()` now reports 38 fields instead of 36. **Constructing `FrontMatter` with a struct literal needs the two new fields**; `..Default::default()` is unaffected.
- Sixteen `COMPONENTS` entries for the floating nav island (`moss-nav-island` and its bar, trail, current, more, actions, sections, menu and progress parts) plus the credit rows (`moss-byline`, `moss-byline-row`, `moss-article-colophon`, `moss-article-colophon-row`, `moss-colophon-label`) and `moss-collection-description`.
- The custom property `--moss-nav-island-display`. Setting it to `none` turns the floating nav island off site-wide; that is the island's entire tuning surface on purpose, since its measure already tracks `--moss-nav-width` / `--moss-content-width`.

### Fixed
- **A footnote back-link is text, not emoji.** The return arrow now emits `&#8617;&#xFE0E;` — U+21A9 plus VARIATION SELECTOR-15 — because without the selector Chrome on Android and iOS picks the emoji form and the arrow renders as a coloured glyph next to plain body text.
- **A bare link at the top of a file is no longer read as frontmatter.** A file beginning `https://example.com` followed by `---` was parsed as the field `https` closed by a delimiter. It is neither — in CommonMark that is a heading and its setext underline — and because that judgement is what tells uid stamping where to write, moss spliced a `uid:` line between an author's link and its own underline, editing the file on disk. `is_frontmatter_field_line` now applies YAML's own rule: a mapping needs a space (or end of line) after the colon. A URL scheme has none, and neither does `mailto:` or `tel:`, so one condition covers every scheme. The stricter reading also stops accepting `title:Hi` in simplified frontmatter — never valid YAML, and rejected by `---`-delimited frontmatter already, so the two forms now agree. Affects `is_simplified_frontmatter`, `simplified_frontmatter_keys` and `parse_simplified_frontmatter`; no signature changes. (The `simplified_frontmatter_delimiter` this version named was folded into `frontmatter::frontmatter_span` in the next one.)

## [0.5.0] - 2026-08-06

### Changed
- The column count a `:::gallery [N]` emits is now the custom property `--moss-gallery-columns`, not `--gallery-columns`. It is written into author-visible HTML as an inline `style=`, which makes it part of the same `--moss-*` surface every other emitted custom property belongs to; it was the only one outside the namespace. No deprecated alias is emitted: it appears in no released `contract.md` and in no `COMPONENTS` entry, so nothing documented pointed at the old name. Custom CSS that overrode `--gallery-columns` directly — undocumented, but writable — needs the new name. The paired `data-columns` attribute is unchanged and remains the supported hook for styling a gallery by column count.
- **BREAKING** — `RenderHooks` has ONE image hook instead of two. `render_image_styled(out, src, alt, title, img_style, width)` is gone and `render_image` now carries that full parameter set; the old four-argument `render_image(out, src, alt, title)` no longer exists. Any downstream `impl RenderHooks` must update both the signature and any call site. The pair was the direct cause of a rendering bug: the trait offered the same concept twice with defaults pointing at each other, so a delegating impl could — and did — forward only the styleless half. The trait's own default no longer discards `img_style` either; a snapshot-less renderer now emits `style=` when one is supplied, where before it silently dropped it. **Breaking API change: bump the minor and update the workspace `moss-core` version constraint.**

### Fixed
- **A misspelled shortcode nested inside a valid one now warns.** A shortcode's body is re-parsed as an independent fragment (grid cells, hero overlays), and both call sites returned only `Vec<Block>` — so the fragment `Document`'s warnings were dropped on the floor. `:::gallry` warned at top level and said nothing inside `:::grid`, which is the case an author is most likely to get wrong, since nesting is where the fence-arity rules bite. The internal `parse_cell_to_blocks` / `parse_overlay_to_blocks` now return `(Vec<Block>, Vec<String>)` and thread warnings up into `Document::warnings`. Neither is public API; consumers see only the extra warnings.
- **Three false claims removed from the published contract.** `moss describe --json` is what moss tells a coding agent to treat as the source of truth, so a wrong entry there is acted on rather than questioned. (1) `moss-unknown-shortcode` published its `example_markdown` as Hugo's `{{< foo >}}` — moss cannot parse that, so the one entry an agent reads *after* misspelling a shortcode taught it a second unparseable syntax; it now shows the real `:::foo` fence and the `data-name` attribute the emitter writes. (2) `tags` described itself as "content tags for organization", which reads as a promise of tag pages; moss generates no `/tags/` routes, so a link to one 404s. The description now states what tags do (merged with inline `#hashtags`, emitted as `article:tag` and JSON-LD keywords) and what they do not. (3) `:::recent` was advertised as an authorable component, but on a web page it renders only its fallback body — the live list is reachable only from the email-digest path. `:::recent {count=5}` with no body produced no HTML, no warning and no literal text; it now warns and names the alternative.
- **An image embed inside a `:::hero` overlay keeps its sizing tokens.** `![[photo.jpg|cover left]]` published `<img src="/photo.jpg" alt="">` in a hero while the identical embed in body prose kept `style="object-fit:cover;object-position:left"` — so the one place the syntax is most often reached for, a cropped hero image, was the one place it did nothing. Authors had no way to tell from the source that the tokens were being discarded. Fixed structurally rather than at the call site (see the `RenderHooks` change above), so the fit/position an author writes now reaches the `<img>` on every path that renders one.
  - **Two knock-on changes to published hero HTML, both bringing overlays in line with body prose.** A heading nested inside a `:::grid` *inside* a hero overlay no longer carries `moss-heading-anchor` — previously the suppression was lost at the nested-shortcode boundary, so a grid heading in a hero kept the `#` permalink that a plain hero heading did not. The `id=` is unchanged, so existing deep links still resolve. Separately, a figure carrying a `data-width` token inside a hero overlay now advertises the `sizes=` for that width band rather than the content-column default, matching what the same figure already declared in body prose; this affects which srcset rung a browser picks, never which image is shown.
  - **An embed with fit/position inside a hero overlay no longer gets an LQIP blur-up placeholder.** The synthesizer suppresses its own `style=` when an embed supplies one, so the two declarations cannot collide — the same trade body prose has always made. Only embeds that specify fit/position are affected.
- **Footnotes and strikethrough render again.** `~~text~~` produced `text` with the formatting gone, and a footnote lost its marker entirely while the definition reappeared as a stray paragraph at the end of the body. Inside a list item it was worse: `- ~~gone~~ stays` split the item into two paragraphs. This was a regression, not a gap — `parser_options` has always set `ENABLE_STRIKETHROUGH`/`ENABLE_FOOTNOTES`, and the pre-`ad86f65b3` (2026-05-28) event pipeline rendered both; when the typed AST became the sole HTML path, `Block`/`Inline` modelled neither, so the events fell into catch-alls that emit nothing and advance a single event — which is why a definition's inner blocks got re-parsed as top-level prose. Now modelled as `Inline::Strikethrough`, `Inline::FootnoteRef` and `Block::FootnoteDefinition` (ADR-035), with numbering, hoisting and endnote emission in `ast/footnotes.rs`. Contract: numbering follows **first reference** (not definition order); a repeated reference yields one endnote with one backref per reference site; a definition written inside a blockquote/callout/list is **hoisted** out and numbered normally; an unreferenced definition still renders its text; a document with no footnotes is byte-identical to before. New classes `moss-footnotes`, `moss-footnote-ref`, `moss-footnote-backref`.
  - **In principle this reaches past "sites using footnotes," but measurably it does not.** Because `ENABLE_FOOTNOTES` was on the whole time, a `[^label]` written in ordinary prose — a regex character class, a shell glob, a `[^…]` example outside a fenced block — becomes a numbered superscript as soon as the same page happens to carry a matching `[^label]:` line, and before this fix it was swallowed outright. Escape as `\[^` or fence the snippet. A token with **no** matching definition is not a reference at all: it renders verbatim, and the page description now keeps it verbatim too, so the two can no longer disagree about the same characters. Incidence was then measured across every page hosted on mosspub.com (2,347 pages, 52 sites): **zero** occurrences inside code or `<pre>`, and four incomplete `[^` in prose that were never valid references and are unaffected. Code spans and fenced blocks are never parsed as footnotes, which is where this digraph almost always lives.
  - **Hoisting a note leaves nothing behind where it used to be.** A definition the author wrote inside a blockquote, a list item or a callout is nested under that container, and moving the note to the endnotes emptied it: `- [^a]: note` published `<ul><li></li></ul>` — a bullet with no text — and `> [^a]: note` a stray blockquote landmark. A container the hoist emptied is no longer published, and a callout keeps its box and title but drops the empty body. A container the AUTHOR left empty (`- one` / `-` / `- two`) still renders: this is about the note moving out, not about tidying markup. So does a container holding only whitespace the author typed — a no-break space, or the full-width `　` (U+3000) CJK writers use for indentation — which an earlier form of this fix read as residue and deleted, taking the surrounding list, blockquote or callout body with it when it was the only item.
  - **A note written above a section no longer steals that section's anchor.** Heading ids were numbered in source order while the renderer hoists definitions to the end of the page, so a heading inside `[^a]: ## Notes` written before a body `## Notes` took `#notes` for the endnote copy and pushed the visible section to `#notes-1` — while `[[Note#Notes]]`, and any existing permalink, still pointed at `#notes` and landed the reader in the endnote list. Ids now follow the order the page actually renders: the body first, then the endnotes in the order they are listed. Only pages with a heading inside a footnote definition are affected.
  - **RSS footnote anchors are scoped per article.** A feed concatenates items into one document, so three footnoted articles would have shipped three `id="fn-1"`s and clicking footnote 1 in article 3 would jump to article 1. Feed HTML now prefixes every footnote id and fragment href with the article's URL path. Newsletter email carries its own footnote arms (see below) and emits no anchors at all, so it has nothing to scope.
  - **Footnotes reach newsletter email.** Email deliberately parsed with footnotes disabled, on the reasoning that walkers without footnote arms would delete note text. Disabling them is not the safe side of that trade: to CommonMark, `[^label]: https://example.com` with footnotes off is a **link reference definition**, so the line was consumed and emitted nothing — a URL-bodied note, the ordinary shape for a citation, vanished outright from mail that cannot be rebuilt after sending, while the web published it as an endnote. A referenced one fared no better, arriving as a link labelled `^label`. Email now renders footnotes: a superscript number in the body and the notes collected at the end, hoisted and numbered exactly as the page numbers them. No fragment links — mail clients rewrite the document and drop the ids, so the anchor would land nowhere.
  - **A footnote written above the opening paragraph no longer becomes the page description.** The description walk skipped the `[^a]:` line but not the rest of the note, so a citation that wrapped onto a second source line — or continued in an indented paragraph — supplied the `<meta name="description">` and the OG tags. Since the renderer hoists the note into the endnotes, the description quoted text a reader never meets at the top of the page. The whole definition block is skipped now — the doc-order-first one, which is the one the renderer hoists; a repeated label's second definition renders in place on the page, so its text stays description-eligible, marker stripped. The description also reads `$…$` with the site's `[site].math` setting, the same way the page parses it, so a `[^…]` the page displays inside an equation is no longer deleted from the meta tags.
  - **A repeated label whose first definition is nested inside another note renders again.** Hoisting decisions were made by a walk-order counter; the body pass skips a hoisted note without descending, so a definition nested inside it was never counted and a later top-level repeat of that label passed for the first — treated as hoisted, it emitted nothing, and the author's text reached no surface at all. Hoisting is now decided by identity (is this the doc-order-first definition of its label — the same lookup the endnote section renders from), which no walk order can corrupt. The same identity now also drives first-reference numbering — a marker living only in a repeat's in-place body, or met inside a never-referenced note's endnote body, is numbered where the reader meets it, not banished to the end — and the cover-image query, so a repeat's image counts as body matter even when the label's first definition is nested inside another note, and a page whose only images live in endnotes takes its cover from the first note the reader meets (index order), not the first the author wrote.
  - **An endnote's image no longer becomes the page's social card.** The auto cover picked the first image in *source* order while footnote definitions render *last*, so writing `[^a]: ![diagram](d.png)` under the paragraph that cites it — the ordinary habit — handed the diagram the `og:image` over the photo the reader actually meets in the body. Body images now win; a note's image is still used when it is the page's only one.
  - **Task lists render as checkboxes.** `- [ ] todo` / `- [x] done` produced the literal `<li>[ ] todo</li>`; they now emit a disabled `<input type="checkbox">` at the head of the item, matching Obsidian. moss's compatibility target is Obsidian, not CommonMark — a vault has to render the same in both places, so "CommonMark-correct" was the wrong standard here. Modelled as a fourth variant, `Inline::TaskMarker(bool)`, because `Event::TaskListMarker` is emitted *inside* `Tag::Item` (ADR-035 § Task lists, amended). Enabling the flag without that variant would have deleted the checkbox while keeping the item text — measured, and now covered by a regression test. Styled via `:has()` on the checkbox itself — both the tight shape (`li > input`) and the `<p>`-wrapped shape loose/nested items produce (`li > p > input`) — no new class, so the component contract is untouched. Newsletter email keeps the state as literal `[x] ` / `[ ] ` markers instead of a checkbox — mail clients strip form controls, which would delete the state from the one surface that cannot be rebuilt after sending.
- **Two headings with the same title no longer share one anchor when one of them sits in a shortcode.** A heading inside a `:::grid` cell, a `:::hero` overlay or a compound-link card was numbered by a counter local to that cell, so a page with `### Notes` in a grid and `## Notes` in the body published **two** `id="notes"` — and `#notes`, from the section's own permalink, from a `[[Page#Notes]]` wikilink, or from any external deep link, scrolled to whichever came first in the page rather than to the author's section. Two same-titled cells in one grid collided the same way with no body heading involved. The page's parse is now the **only** pass that numbers ids: a cell, overlay or card is parsed through an entry point that leaves its headings holding bare base slugs, and the page walk numbers every one of them in render order. Numbering in both places suffixed twice — a single cell holding two `### Notes` arrived as `notes`/`notes-1`, and the page walk then bumped the first to `notes-1` (colliding with the second) and the second to `notes-1-1`, a shape no slug rule can produce — so the earlier form of this fix moved the duplicate rather than removing it. Every anchor on a page is unique again. **Upgrade note:** where this fired, the anchor moves. The copy that renders FIRST keeps the bare `#notes`, and the later one becomes `#notes-1` — so on a page whose grid card precedes a same-titled section, links to that section must now use `#notes-1`. Only pages that were already publishing duplicate ids are affected; a page whose headings were already unique is byte-identical.
- **A line break inside image alt text is a space, not nothing.** An Obsidian author who soft-wraps a caption across two source lines — `![Cover art\nby Jane](c.jpg)` — got `Cover artby Jane` in both the `alt=` attribute and, via the implicit-figure path, the visible `<figcaption>`. The break now flattens to a single space, the way browsers and Obsidian flatten it and the way newsletter email already did, so the same markdown no longer reads differently on the web than in the mail. An **explicit** break (backslash or two trailing spaces) still renders as a `<br>` inside the `<figcaption>` while the attribute takes the space — the only flattening an attribute allows.
- **A nested image's alt text no longer truncates and its trailing words no longer leak out as separate body prose.** `![a ![b](inner.png) c](outer.png)` is valid CommonMark and, per the image-alt-flattening rule, is ONE `Inline::Image` — but the alt-collection loop (`ast/parser.rs`'s `Tag::Image` arm) stopped at the FIRST `End(Image)`, which belongs to the INNER image, not the outer one. The published page truncated the alt to `"a b"` and leaked the trailing `" c"` out as a separate, visible paragraph inline — text the author wrote inside an image's description, appearing as body prose no reader would expect there. The loop now counts nesting depth (matching newsletter email's own `image_depth` counter) and only stops at the outer image's own matching close. Only a paragraph containing a nested image construct is affected; an ordinary, unnested image is unchanged.
- **CJK-friendly emphasis.** `**…**` / `*…*` around CJK text now renders bold/italic even when the closing delimiter sits between CJK punctuation and an ideograph with no ASCII space (e.g. `**这句话。**下一句` → **这句话。**下一句). Vanilla CommonMark flanking treats that closing `**` as non-right-flanking and leaves it literal; `parser_options` now sets `Options::ENABLE_CJK_FRIENDLY_EMPHASIS`, implementing the [`tats-u/markdown-cjk-friendly`](https://github.com/tats-u/markdown-cjk-friendly) amendment to CommonMark 0.31.2 (backward-compatible on all existing CommonMark examples). The flag is inserted under moss-core's off-by-default `cjk-friendly-emphasis` feature — the app turns it on, and with it off the published crate still builds against crates.io. Until the flag ships in a pulldown-cmark release ([#1059](https://github.com/pulldown-cmark/pulldown-cmark/pull/1059)), it is supplied via a workspace `[patch.crates-io]` fork (the v0.13.3 release plus only the PR's CJK-emphasis commits, so no other behavior changes).
- `[site].implicit_figure = false` is now honoured inside footnote definitions. The opt-out walks the block tree unwrapping promoted figures, but its container list omitted `Block::FootnoteDefinition`, so a site that had explicitly opted out still published a `<figure>`/`<figcaption>` for an image written in an endnote. The container arms are now one `|`-combined match, and the doc comment names the two variants deliberately excluded (`Shortcode`, whose cells run the walk in their own parse, and `Table`, whose cells hold inlines and can never contain a figure) so the next block-holding variant sees the obligation.

Callers wrapping `HeroOverlayHooks::new(&inner)` become `DefaultHooks::hero_overlay(assets)`; a downstream impl that wants anchor-free headings overrides `emit_heading_anchors` rather than re-implementing heading HTML.

### Added
- **BREAKING (struct literal)** — `Document::warnings: Vec<String>`. The shortcode extractor has collected unknown-name warnings since the fallback landed, but nothing carried them out of `parse()`, so a misspelled `:::gallry` rendered an empty div and the build said nothing. The field carries them to the caller; the app pipeline prints each against the file. `Document` derives `Default` and the field is `#[serde(default)]`, so `..Default::default()` construction and existing serialized documents are unaffected — but an exhaustive struct literal `Document { blocks, block_meta }` no longer compiles. **Bump the minor and update the workspace `moss-core` version constraint.**
- The `article-masthead` classes are declared in the component contract: `.date-line`, `.date`, `.site-name`, `.breadcrumb-segment`, `.nav-icons`. The renderer already emitted all five and `describe --json` had nothing for any of them, so the only way to find them was to read built HTML — which the shipped guidance permits only as a self-check, and which breaks silently the day a class is renamed. Found by watching an agent given a real site and the words "restyle this site" reach for the byline row first and come up empty. They keep their legacy non-`moss-` prefixes on the precedent `main-nav` set, and carry a comment recording that `components_sync_test` cannot guard them (it matches only `class="moss-..."` literals).
- `moss describe --json` publishes the recognized language codes. Nothing could previously answer "which directory names make a language edition?" before the directory was created, and the failure that hides behind is silent: an unrecognized name is not an error, so an agent that invents `english/` gets no signal that it built nothing.
- Inline `#tags` written in body text now count toward a page's published tag metadata. Obsidian authors tag in prose at least as often as in frontmatter, and moss read only `tags:` — so a typical vault note silently lost every inline tag on publish (`article:tag` meta, JSON-LD keywords). New pure walker `ast::tags::extract_inline_tags` collects them from the typed AST under Obsidian's exact grammar: a `#` at a line start or after whitespace **in the source** opens a tag (URL fragments and mid-word `a#b` never match); tag characters are everything outside Obsidian's exclusion set, so CJK and emoji tags work and `#a/b` is one nested tag; `^` is part of that exclusion set (Obsidian reserves it for `^block-id`s), so `#foo^bar` yields `foo`, not `foo^bar`; the walker re-joins adjacent text runs and threads sibling context, so a tag pulldown splits at an emphasis delimiter (`#_draft`) is still extracted while a `#` right after a closing delimiter or inline construct (`*emph*#x`, `` `code`#x ``, `[link](u)#x`) is not; purely-numeric `#123` is rejected; results dedupe case-insensitively keeping the first-seen form in document order; code spans and fenced blocks never yield tags. The walk covers every construct whose text the page publishes — including a callout's **title** line (`> [!note] Recipe #cooking`) and the prose inside `:::grid` cells, `:::hero` overlays and compound-link cards, all of which Obsidian indexes and moss renders as ordinary visible text. The page's tag set is the **document-level** union — frontmatter `tags:` first, then inline tags not already present (case-insensitive) — made where the app pipeline unpacks frontmatter, deliberately never in the folder cascade: the cascade's uniform child-overrides-folder rule is unchanged, so a doc with any tags of its own (either kind) blocks folder-cascade tags exactly as before, and a doc with no tags anywhere still inherits them. Rendering is untouched — the tag text stays visible as plain prose, because Obsidian's tag-as-link points into its own search UI and a published site has no tag page to link to. Known limits: pulldown-cmark erases the backslash of an escaped `\#tag` before the AST exists, so escaped tags are extracted too; a callout title is stored as a plain string, so the sibling-context rules do not apply inside it; and a `:::recent` zero-match fallback body is unparsed markdown, so tags written only there are not indexed.
- `ParseConfig::hard_line_breaks` and `ast::line_breaks::apply`, off by default. When enabled, a single newline inside a paragraph renders as `<br>`, matching Obsidian's default (`strictLineBreaks = false`, i.e. remark `breaks: true`); CommonMark treats the same newline as a space, so the most ordinary markdown there is — a paragraph wrapped across two lines — renders differently in Obsidian's preview and on a published moss site. pulldown-cmark 0.13 exposes no hard-break option (verified: the fork's `Options::all()` is 17 flags, none of them `breaks`), so this is a post-parse transform over the typed AST. It is exact, not heuristic: `parse_inline` maps `Event::SoftBreak` to `Inline::Text("\n")` and pulldown splits every line break into its own `SoftBreak`, so a `Text` inline never carries a newline inside a longer run — matching `Text == "\n"` hits soft breaks and nothing else. Code blocks are structurally untouched (their body is a `String`, never walked). The flag follows `math`'s precedent — default `false` at the crate level because it changes what the author's characters mean, so library consumers and fixtures keep CommonMark unless they opt in. The app resolves `[site].hard_line_breaks` to **on by key absence** (Obsidian parity — the vault renders the same while being written and once published); `[site].hard_line_breaks = false` restores CommonMark. Measured before flipping (mosspub.com, 2,347 pages): 4.8% of pages gain a break, concentrated in one demo site; poetry sites measured zero because their authors already write explicit breaks.
- Responsive-image ladder vocabulary in `asset_paths`. `ladder_rungs(natural_w, natural_h, is_animated) -> &'static [u32]` is the shared pure oracle that decides which width variants exist for a source; `deployed_width(natural_w, natural_h)` returns the width the base variant actually ships at (the longest edge capped to `DEPLOY_MAX_EDGE`); `to_webp_rung(source, width)` derives a rung URL (`photo.jpg` + 800 → `photo.w800.webp`); `DEPLOY_MAX_EDGE` (2400) and `LADDER` (`[800, 1600]`) are the single source of truth the encode pipeline's `ImageCompressionConfig::default()` also reads. Both `ladder_rungs` and `deployed_width` are **height-aware** on purpose: the encoder caps the longest *edge*, not the width, so a portrait source's deployed base and its rungs are computed from `max(w, h)` — passing width alone silently over-promises rungs for tall images. The function is deterministic in scan-derived inputs only (dimensions + animated flag), never encode/cache state — that constraint is what lets the registration loop, the encode worker, and the synthesizer agree by construction (ADR-013: never emit an unregistered `<source>`). `is_ladder_source_ext(ext)` and `is_webp_source_ext(ext)` are the single extension gates shared across the six pipeline census sites and the synthesizer.
- `contract::sizes`: per-render-context `sizes=` attribute table (`SIZES_FULL_BLEED` = `100vw`, `SIZES_BODY`, `SIZES_CARD`, `SIZES_GALLERY`), encoding the default theme's layout widths off `site.css` tokens. Part of the theme-author contract surface; no override machinery yet (a theme that changes layout gets slightly-suboptimal, never-broken fetches). Lives in a new consts-only module beside `tokens`/`components` under `contract/` (not inside `components.rs`).
- `AssetSnapshot::animated` (a `HashMap<PathBuf, bool>`) and its `is_animated(&PathBuf) -> bool` accessor (missing key reads `false`). The synthesizer consults it to suppress the responsive ladder for animated sources (multi-frame GIF / animated WebP), which must never be re-encoded into still rungs. Populated from scan metadata's new `is_animated` flag.
- LaTeX math parsing, off by default. `ParseConfig::math` gates pulldown-cmark's `ENABLE_MATH`, so `$…$` and `$$…$$` become `Inline::Other` nodes rendering the equation's own source — **`$` delimiters included** — HTML-escaped, in `<code class="moss-math" data-moss-math="inline|display">`. The delimiters are part of the payload because P1 has no typesetting engine: the span is what the reader sees, so emitting only the inner TeX would silently delete two characters of the author's prose. That is not hypothetical — `一个$5，两个$10` parses as math (a full-width comma is non-whitespace, so it closes the span) and would have reached readers as `一个5，两个10`. A genuine equation therefore shows a visible `$…$` until a typesetting phase replaces the span. There is no typesetting engine in moss-core (ADR-030 keeps it app-side); this is the honest-fallback layer a renderer later upgrades to SVG. Existing callers are unaffected: `ParseConfig::default()` leaves math off, `$` stays an ordinary prose character, and no committed fixture changes.
  - Enabling math **without** handling both events silently deletes every equation — `Energy $E = mc^2$.` parsed to `<p>Energy .</p>`, because the AST walker's catch-all arms drop unrecognized inline events. The handler arms and the `parse_inline_event` whitelist entry that prevent this are covered by `tests/math_parsing.rs`, including math nested in list items — the wiring path a paragraph-only test cannot see, since `collect_item_blocks` is that whitelist's only caller. Math in table cells, blockquotes, links, callout bodies and footnotes reaches the parser by other routes and is covered separately.
  - `tests/fixtures/math-delimiters.vectors.json` records pulldown's `$` open/close rules as measured golden vectors — the cross-language contract a future editor grammar must agree with. The rule that decides every false positive: a closing `$` must be immediately preceded by a non-whitespace byte. `$5 and $10` survives only because the second `$` follows a *space* — that is a habit of English typography, not a property of ASCII or of currency. Put any punctuation between two prices and the span closes: `$5-$10` (price range), `$5/$10` (tiers) and `$9.99 ($8.99 for members)` (parenthetical) all parse as math, in English prose, on a default site. Unspaced CJK (`一个$5，两个$10`) parses for the same reason — a full-width comma is non-whitespace. In every case the text stays byte-exact, because the fallback keeps the delimiters; what changes is *presentation*, since the run renders in a monospace `<code>` span on published pages and in RSS item content. Any site whose prose puts two `$` in one paragraph without a space before the second should set `math = false` or escape as `\$`.
  - **Upgrade note — headings whose math contains `*`.** `[site].math` defaults to on, so upgrading enables math for sites that never set the key. Heading anchors normally survive that flip untouched, because the slug is computed from the equation's restored source. They do **not** survive when the TeX contains markdown-active characters: with math off, intraword `*` is eaten as emphasis first, so `# Convolution $f*g$ and $h*k$ end` was published as `convolution-$fg$-and-$hk$-end` and becomes `convolution-$f*g$-and-$h*k$-end`. `# Dual $V^*$ and $W^*$ end` moves the same way, and dual-space notation is common. Where this fires, external deep links, in-page TOC entries and `[[Page#Heading]]` wikilinks pointing at the old anchor break. Set `math = false` to keep the published anchors. See ADR-030 §"Upgrade-time anchor movement".
- `RenderHooks::render_math(out, tex, display, fallback_html)` takes a `fallback_html` argument (P2, ADR-030). moss-core stays engine-free — its default impl emits the escaped-source `<code class="moss-math">` chip — but the app override typesets `tex` to an inline `<svg>` via RaTeX and, when its crash-safety envelope refuses (oversized / deeply-nested / CJK / malformed input), emits `fallback_html` instead. Passing the pre-rendered fallback keeps moss-core from having to know either the engine or the fallback markup. Same-cycle refinement of the unreleased `render_math`; no released signature changed.
- `ast::parser_options(math: bool)`: the single constructor for moss's pulldown-cmark option set (strikethrough, tables, footnotes, wikilinks, plus math on request). Parser construction had drifted across five independent sites; call this instead of assembling `Options` by hand, and where a site genuinely needs a different set, call it and remove the option explicitly so the divergence stays visible.
- `link_completions::rank_completions`: deterministic ranking for wikilink/embed completion candidates. Sort keys: trigger-kind fit, prefix-at-start match quality, same-language-tree as `from_file`, directory-tree proximity, insert-value length, then lexicographic tiebreaks — mirroring `content_graph`'s resolver tiebreak chain so the dropdown surfaces the candidate a `[[link]]` would actually resolve to.
- `resolve::md_extract`: pure markdown reference extractor (`extract_md_references`) returning every wikilink / embed / markdown-link / markdown-image token with byte offsets. Zero I/O; backs rename-with-references and delete-with-references in the editor.
- `frontmatter::strip_control_chars_str`: strips stray C0/C1 control characters (excluding TAB/LF/CR) from a string. Applied at the frontmatter write boundary as defense-in-depth against a macOS Tauri multiwebview bug that can type raw arrow-key control codes into text inputs (`tauri-apps/tauri#10194`); exposed `pub` so other crates' write paths can apply the same strip.

### Fixed
- The implicit-figure `<figcaption>` now renders its alt content as inline markdown (Pandoc's implicit-figure model): `*em*`, `[links](…)`, `` `code` `` and math survive as typed AST nodes instead of being flattened to plain text — so `![before *em* and $x^2$ after](p.png)` captions with `<em>em</em>` and a typeset equation (via `RenderHooks::render_math`) rather than stripped markers and raw `$x^2$` source. The `alt=` attribute is unchanged: it stays the flat plain-text source (math delimiters verbatim) for assistive tech and blocked-image fallback. Wikilink-embed captions (literal pothole alias, not markdown), width-carrying alts (`![cap|50%](p)`), and plain-text alts keep their previous byte-identical output.
- Section-scoped embeds with a human-readable anchor (e.g. `![[file#Heading With Spaces]]`) now slugify the target before matching, so they inline just the referenced section. Previously the raw anchor was compared against slugified headings, never matched, emitted a spurious `Heading '#...' not found` diagnostic, and fell back to inlining the entire file. Anchors already in slug form are unaffected.

### Changed
- Doc-only: the `asset_paths::ladder_rungs` deterministic-agreement contract now records that the **EXIF-orientation agreement holds unconditionally**. The app-side scan-swap fix (responsive-image-variants design follow-up #1) makes scan store the oriented display dims for EXIF-rotated png/webp/jpeg, so the census sites and the encode side derive the identical ladder for those too — the prior "holds except for EXIF-oriented png/webp" exception (and its `render/image.rs` back-references) is removed. No code or behavior change in this crate.
- Raster-original rendering (`render/image.rs`) now emits a **responsive multi-width `srcset`** instead of the single-URL WebP `<source>`. For png/jpg/jpeg sources the `<picture><source>` gains a ladder — `srcset="photo.w800.webp 800w, photo.w1600.webp 1600w, photo.webp 2000w"` with a context-appropriate `sizes=` — the top descriptor being the base WebP at its deployed (edge-capped) width. For **webp** sources (previously a bare `<img>`) the ladder attaches **directly to the `<img srcset>`** with no `<picture>` wrapper, since the base `src` is already WebP. Sources at or below the first rung (≤800px), animated sources, and unknown-dimension sources fall back to the pre-feature single-URL shape byte-for-byte; `EmailBody`, og:image, logo, favicon and bare-fragment contexts never carry `srcset` and are unchanged. Rung existence is decided by `asset_paths::ladder_rungs` from the same scan-derived dimensions the build pipeline registers and encodes, so every emitted rung URL is a promised (`set_pending`) variant — ADR-013 holds by construction.
- `render/image.rs` ladder `srcset` URLs now percent-encode literal commas (`,` → `%2C`) in each candidate URL (`encode_srcset_url`), so a comma-named source (`a,b.jpg` → `a%2Cb.w800.webp 800w, …`) no longer mis-splits the comma-delimited candidate list in browsers or the html_post rewriter (responsive-image-variants follow-up #4). Only the ladder `srcset` candidates are encoded — the base `<img src>`/legacy single-URL `<source>` keep their literal comma (a single unambiguous URL). A static file server decodes `%2C` → `,` to the on-disk `a,b.w800.webp`. Comma-free filenames are byte-for-byte unchanged.
- **BREAKING** — the heading modules are consolidated under one parent. `moss_core::extract_headings::` is now `moss_core::heading::extract::`, and `moss_core::heading_anchor::` is now `moss_core::heading::anchor::`; both old module paths are gone. The commonly-used items keep working through re-exports — `moss_core::extract_headings`, `moss_core::HeadingInfo` and `obsidian_heading_anchor` are all still reachable via `heading` — so only code that named the old *module* paths must change. Heading logic previously lived in four homes with no single owner of "what is a heading's text?"; P1's math work had to keep the math-on slug, the rendered `<hN id>` and the wikilink graph's raw-line slug in agreement across all of them, and a false anchor invariant survived review partly because no one module owned the answer. Folds into the same minor bump the `PageKind::Asset` removal already requires (0.1.x → 0.2.0).
- `ComponentEntry::is_public()` now also returns `false` for internal implementation classes (`moss-apply*`), hiding them from `moss describe` and `docs/reference/contract.md`.
- Subscribe-form contract: `moss-subscribe-form` now always uses `data-position="inline"` (the auto-injected email footer and the `:::subscribe` shortcode emit identical HTML; footer vs in-page styling keys on the `footer` ancestor). Adds a `data-button-override` attribute, emitted when an author overrides the button label (`:::subscribe{button="…"}`); on such forms `subscribe.ts` leaves both the button label and the placeholder as authored instead of overwriting them with the language default. The former `data-position="footer"` value and the `footer-shape` slot / `data-moss-shape` footer attribute are removed.
